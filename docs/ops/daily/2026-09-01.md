## 2. 実装（優先2）

`src/lib/extract/twitter.ts`。**問題は「401 で失敗すること」ではなく「401 が失敗として記録されないこと」だった。**

### 直した穴

fx-api / fx-direct / fixer（`scrapeFixer`）の 3 か所とも、条件分岐が名指ししていたのは
`403|429`（cooldown＋`sawBotChallenge`）・`404`（`POST_NOT_FOUND`）・`ok`（解析）の 3 つだけで、
**それ以外のステータスはどの枝にも入らないまま次のフォールバックへ落ちていた**。
本番が 53 日間 返し続けている **401 がまさにこの「名前のない枝」**で、
結果として **全滅している extractor 自身のログに `provider_failed` すら 1 行も出ない**状態だった。

### 変更内容

- **`classifyProviderStatus(status)` を純関数として切り出し**（テスト可能な単位にするのが目的）:

  | status | class | failure ラベル | cooldown |
  |---|---|---|---|
  | 401 | `unauthorized` | `PROVIDER_UNAUTHORIZED` | **有** |
  | 403 / 429 | `bot_challenged` | `BOT_CHALLENGED` | 有 |
  | 404 | `not_found` | `POST_NOT_FOUND` | 無 |
  | 200–299 | `ok` | `null` | 無 |
  | **その他すべて** | `http_error` | `PROVIDER_HTTP_<code>` | 無 |

- fx-api / fx-direct は非 ok を **`httpStatus` 付きで `provider_failed` に出力**する。
- `scrapeFixer` は非 ok を**ラベル付きで throw** する（呼び出し側の既存 catch がそのままログに乗せ、
  従来の「`[]` を返して次の candidate へ」と同じ制御フローになる＝挙動は非変更）。
- **ユーザー可視の最終エラーは意図的に非変更**。401 では `sawBotChallenge` を立てないため、
  最終エラーは従来どおり `MEDIA_NOT_FOUND` のまま（今回の目的は診断可能性であって UX 変更ではない）。
- テスト `src/lib/extract/twitter-provider-status.test.ts` を追加（6 ケース）。
  最後の 1 ケースは**「使えないステータスに `failure: null` を返さない」という契約そのもの**を
  14 ステータスで固定する＝今回の穴の再発検知が目的。**vitest 84 → 90**。
