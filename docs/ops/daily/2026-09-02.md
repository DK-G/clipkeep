### 設計上の判断 2 点

1. **公開 API 越しの黒箱テストにした。** `checkInMemory` は module-private であり、
   export を足せばテストは書きやすくなるが、それは成功指標の「production 非改変」を崩す。

2. **時刻は fake timers ではなく `Date.now` の spy で制御した。**

   fake clock を入れるとこのタイマーまで巻き込まれる。時刻源だけを差し替えるのが最小の介入。

なお in-memory バケットは module state で**ファイル全体で共有される**ため、各テストは連番付きの
新しいキーを使う（`freshKey()`）。これを怠るとテスト間で干渉して偽陽性/偽陰性が出る。

### 固定した契約（21 ケース）

- **`getClientKey`**: `cf-connecting-ip` 優先／空白のみのヘッダは「無い」扱いで `x-forwarded-for` へ／
  xff は**先頭要素＝クライアント**（間のプロキシではない）／両経路とも trim ／
  帰属不能な呼び出しは throw せず `unknown` に集約。
- **窓と上限**: ちょうど `limit` 件まで通し次を弾く／env 未設定時の既定は 30 件/60s ／
  返り値の `limit`・`windowMs` は**実際に適用した値**を報告する。
- **retry-after**: 最古のリクエストが窓から抜けるにつれ減る（10s 経過で 50、59s 経過で 1）／
  **窓長を超える値を絶対に出さない**。
- **キー分離**: あるクライアントが他のクライアントの予算を消費しない。
- **拒否時に予算を二重消費しない**: 弾かれた試行は窓を延長しない（弾かれ続けても最初の 1 件は自分の予定どおり抜ける）。
- **DO 経路**: 正常応答は採用し `source: 'do'`／`key`・`windowMs`・`limit` を DO へ転送している
  （＝DO 側が同じポリシーを適用できる）／`retryAfterSec` 欠落は 0 とみなす。
- **★DO 劣化時に fail-closed であること**: 非 2xx・パース不能 body・`limited` が boolean でない・
  `limited` 欠落・fetch が throw の **5 通りすべてで in-memory へ落ち**、
  **落ちた先でも上限をローカルに適用し続ける**（＝「DO が死んだら無制限」にならない）。
- `RATE_LIMIT_DO_ENDPOINT` が未設定/空白なら fetch を**一切呼ばない**。

### 本番検証（DoD 5）

本タスクは production 非改変のため、「変更箇所の目視」ではなく
**固定した契約が本番で実際に成り立っているか**を直接叩いて確認した。
`app/api/v1/extract/prepare/route.ts:44` はレート制限を **Turnstile より前**に評価するため、
CAPTCHA を回避することなく（＝上限到達までは 403 `TURNSTILE_MISSING` が返るだけ）計測できる。

`POST https://clipkeep.net/api/v1/extract/prepare` を連続実行:

- 1〜31 件目: **403**（レート制限は通過し Turnstile で停止＝設計どおり）
- 32 件目以降: **429** `RATE_LIMITED`
- 応答ヘッダ: `x-rate-limit-source: do` / `x-rate-limit-limit: 30` / `x-rate-limit-window-ms: 60000`
- 応答 body: `{"retryAfterSec":54,"source":"do","limit":30,"windowMs":60000}`

確認できたこと:

- **本番で実際に走っているのは `do` 経路**（in-memory fallback ではない）。
  ＝今回テストで固めた in-memory 側は**「DO が落ちた時の縮退先」としての価値**であり、
  fail-closed を固定した意義はまさにそこにある。
- `limit` / `windowMs` が bindings の値と一致し、**返り値が実際に適用した値を報告している**という契約が本番でも成立。
- `retryAfterSec: 54` は **0 < x ≤ 60**＝「窓長を超える retry-after を出さない」契約が本番でも成立。
- ★**429 に転じたのは 31 件目ではなく 32 件目**。これは**分散カウンタ（DO）側の境界**であって、
  今回テストで固めたクライアント側モジュールの境界とは別物である。
  **「本番の上限はちょうど 30 件目で切れる」とは言えない**（DO の窓開始時刻に依存する）。
  ローカルで固定したのはあくまで in-memory 縮退時の境界。
